# MGR 发布前与后续开发路线图

> 整理日期：2026-08-12。范围刻意排除联机专属卡牌、药水与自定义事件；这些内容另行规划。

## 一、当前完成度判断

MGR 已经不是“人物雏形”，而是一套接近发布候选版的完整人物：

- 单人奖励池已有 80 张有效卡：20 白、35 蓝、25 金；分布为 28 攻击、35 技能、17 能力。
- 此外已有 4 张基础牌、2 张先古牌和 3 张衍生牌。
- 已有 11 件职业内容遗物：1 初始、1 先古、2 普通、2 罕见、3 稀有、2 商店。
- 音符、和弦、演奏、强音、起音尾音、星空、幽灵与万象均已形成规则、UI、关键词和动画闭环。
- 人物战斗动画、阴影、营火、商店、选人界面、能量框、先古对话、遗物池过滤和遥测框架均已接入。
- 当前本地化只有简体中文和英文；声音资源主要是选人、生成音符与和弦三组。

结论：继续无上限扩充普通卡牌会降低可控性。下一阶段应以发布质量、平衡数据和玩家理解成本为中心。

## 二、发布前必须完成（P0）

### 2.1 建立完整回归测试表

每次游戏或 RitsuLib 更新后，至少覆盖：

1. 新开对局、保存退出、继续游戏、战斗结束、死亡、胜利。
2. 五种基础音符、星空、幽灵、万象；容量增减、双重和弦、空槽与满槽。
3. 演奏的攻击、技能、能力、状态、诅咒与 X 费牌；自然结束、强制结束、直接入队和立即触发。
4. 敌人中途全部死亡时立刻停止后续演奏。
5. 活动小丑交换、胆小鬼火箭回合末入队、轩辕十四返回手牌等特殊牌堆移动。
6. Adios/延长演奏等队列调度牌的重入保护，确保无法递归自锁。
7. 呀啊啊啊无限升级、随之任之永久伤害、卡牌类型修改等战斗内/跨战斗变更。
8. 地图、卡组、牌堆查看、选牌、商店、营火打开时所有战斗 UI 的隐藏和层级。
9. 遗物的跨战斗计数、锻造触发、替换初始遗物和奖励黑名单。
10. 不同分辨率、窗口缩放、手柄/键盘操作、长文本与大量演奏牌。

完成标准：把发现的问题记录为“复现步骤—日志—预期—实际”，禁止只记录“偶尔卡死”。

### 2.2 自动化静态验证

仓库已有本地只读校验器 `tools/Validate-MgrContent.ps1`，可检查登记表、注册代码、资源、Godot UID、本地化和奖励池数量。后续可把同一检查接入 GitHub Actions：

- 编译：`dotnet build --no-restore /p:CopyModOnBuild=false /p:RunPckExport=false`。
- 解析全部 JSON，检查重复键和非法格式。
- 对照 `MGR_content_registry.json` 检查有效卡牌的 C# 类型、注册键、图片、`.import` 与中英文本。
- 检查遗物的类、图片、本地化与登记项。
- 检查 Godot UID 重复、孤儿资源和同名旧资源。
- 检查被删除/改名内容是否仍残留注册或本地化键。
- 固定输出 20/35/25 的单人奖励池统计，防止衍生牌或联机牌误入奖励池。

这些检查不能替代游戏测试，但能在启动游戏前拦截大量低级错误。人工测试按 `docs/MGR发布前回归检查表.md` 执行。

### 2.3 版本兼容与失败隔离

- 每次游戏测试版或 RitsuLib 更新后记录“游戏版本—RitsuLib 版本—MGR 版本—结果”。
- 检查所有运行时补丁目标；目标签名变化时，应让 MGR 明确报错并停止相关功能，而不是半初始化。
- 为音符、演奏和选牌命令的异常增加足够上下文日志：卡名、牌堆、目标、是否自动打出、队列序号。
- 发布前冻结注册主键；冻结后改显示名不能再改变存档标识。
- 明确 1.0 以后如何处理旧版本存档：兼容、迁移或明确宣布不兼容。

### 2.4 清理文档与资源

- README 仍是早期雏形内容，写着音符 UI 尚未接入，必须按当前状态重写。
- `MGR_CARD_POOL_AUDIT.md` 后半部分仍包含旧卡名、旧数量和已解决问题，需要重新生成。
- 清理未注册脚本、旧图片、旧 `.import`、失效本地化键和历史占位资源。
- 核实人物动画、音乐、卡图和参考素材的使用授权；为第三方工具、素材作者和 RitsuLib 准备 Credits。
- 补充隐私说明：遥测默认是否启用、收集什么、如何撤回授权、数据保存在哪里。

### 2.5 发布包与创意工坊页面

- 更新模组版本号、最低游戏版本和最低 RitsuLib 版本。
- 实际测试“全新用户只安装发布包和 RitsuLib”能否运行，避免开发机缓存掩盖缺失资源。
- 准备简介、依赖说明、安装方式、已知问题、更新日志、截图和演奏机制短视频。
- 为日志位置、崩溃报告内容和标准复现格式写一份玩家故障报告模板。

## 三、发布前强烈建议完成（P1）

### 3.1 平衡测试与奖励质量

卡池数量已达到目标，重点改为：

- 按楼层记录抓取率、跳过率、升级率、删除率和胜率。
- 区分前期过渡牌、对策牌、流派核心、泛用牌与合理弱牌。
- 重点测试第二至第三回合：支付演奏/能力布置费用后是否容易无牌或无能量。
- 检查批量音符、双倍音符、强音和立即触发之间的乘法上限。
- 检查诅咒流能否处理循环污染，但又不会无代价地把诅咒全部变成收益。
- 与机器人、储君等原版人物在相同难度和种子区间对照，而不是只做牌面对比。

当前遥测代码已经接好，但后端地址为空。可以先用本地表格记录；正式启用遥测前必须完成授权文本和隐私检查。

### 3.2 教学、说明与玩家可理解性

建议制作角色专属教程，分阶段出现：

1. 第一次生成音符：解释类型映射、槽位与和弦。
2. 第一次获得演奏牌：解释首次打出不扣次数、后续回合自动打出和结束去向。
3. 第一次遇到起音/尾音/强音/星空/幽灵/万象时，只解释新概念，不一次塞满屏幕。
4. 在卡牌图鉴或人物说明中提供可重复查看的完整机制页。

教程必须可以关闭，且不能在每次新对局重复骚扰熟练玩家。

### 3.3 可访问性与视觉设置

MGR 的动画密度已经高于原版平均水平，建议提供：

- 特效强度：完整 / 精简 / 最低。
- 演奏与音符动画速度倍率。
- 减少闪烁、屏幕震动和强光。
- 音符/演奏牌 UI 大小、位置和透明度。
- 色觉辅助：每种音符必须同时依赖形状和图标，不只依赖颜色。
- 选人音效、音符音效和和弦音效的独立音量。

### 3.4 本地化与文本冻结

- 对简中进行最后一次术语、数字、换行、关键词顺序和能力描述校对。
- 英文不能只保证 JSON 有值，还需检查自然表达、复数、能量图标和动态变量。
- 若社区愿意协助，可在文本冻结后开放日文、繁中等翻译；冻结前过早翻译会不断返工。
- 自动检查卡牌升级前后关键词位置和绿色差异文本。

### 3.5 性能与长局压力测试

- 大量音符、超大音符槽、十余张演奏牌、多次和弦、多个持续形态同时存在。
- 检查所有代码绘制节点能自行释放，粒子数量有上限，战斗结束后无残留引用。
- 记录低配置机器帧率和内存；必要时在精简模式下降低星星、连线和碎片数量。
- 演奏队列保持游戏结算串行，但纯视觉尾迹不能阻塞下一张牌。

## 四、可以继续开发的新内容（不含联机卡、药水、事件）

### 4.1 职业遗物扩展

当前 11 件已经能构成基础，但还可以补 2～4 件，优先填补而非放大已有优势：

- 演奏能量平滑：自然演奏结束或第一次自然演奏时提供有限资源，禁止被立即触发反复利用。
- 音符顺序调度：战斗开始交换、冻结或保留一个音符，而不是继续批量生成音符。
- 诅咒循环：帮助处理当前手牌或抽牌节奏，但不消除诅咒的长期代价。
- 防御成长：提供缓慢、有限的长战防御，不再叠加伤害乘法。
- 可考虑一个真正的职业 Boss 遗物或替换型初始遗物，形成有代价的规则变化。

### 4.2 卡牌附魔与原版系统兼容

- 系统检查所有原版附魔对 MGR 动态伤害、无限升级、演奏、卡牌类型修改和生成牌是否正确。
- 确认演奏自动打出时，附魔只在应触发时触发，不重复应用永久修改。
- 后续可制作少量音乐主题附魔，但附魔属于全局内容，必须确保其他人物拿到也能独立工作。

### 4.3 声音设计

当前主要只有选人、音符生成和和弦声音。可继续增加：

- 不同音符类型的轻微音色差异，但保持统一音量。
- 演奏入队、自然触发、结束演奏和强制结束的短音效。
- 关键能力触发音：卡农轮转、卫星少女、八十八键、万象。
- 极少量人物语音或哼唱；必须避免每回合重复造成疲劳。
- 所有声音先做响度归一化、淡入淡出和多次连续播放压力测试。

### 4.4 人物表现与叙事

- 补充胜利、失败、复活、濒死、队友提示等可实际挂接的角色台词。
- 丰富先古对话的重复分支，并校对中英文语气一致性。
- 为 Boss、特殊房间或关键遗物增加角色反应，但不要修改原版人物或事件逻辑。
- 可以增加人物皮肤、卡背、选人背景变体或高阶解锁外观；纯外观比继续扩卡更安全。

### 4.5 挑战、成就与成长内容

- 角色成就：单回合触发若干和弦、维持大量演奏牌、用诅咒音符回复一定生命等。
- 角色挑战：固定卡组、限制音符类型、改变槽位数量或禁止即时和弦。
- 图鉴统计：最高强音、单场和弦、演奏次数、万象触发数。
- 解锁内容应以外观、挑战或少量卡牌为主；不要让基础角色必须先玩其他人物才能使用。

### 4.6 数据分析与平衡工具

- 启用自有 PostHog/Cloudflare 后端，或制作本地 JSON/CSV 导出模式。
- 增加 MGR 聚合字段：每场和弦数、演奏牌数、不同音符占比、诅咒生成量、强音峰值。
- 不上传逐帧 UI、设备隐私或完整日志；所有新增字段提升 schema 版本。
- 制作简单的抓牌率—胜率—楼层交叉报表，避免仅凭少数高光局调整强度。

### 4.7 社区与扩展接口

- 为其他模组公开稳定的“卡牌转音符”“生成音符”“加入演奏队列”接口，而不是让作者调用内部状态。
- 定义哪些 API 在 1.x 保持兼容，哪些仍是内部实现。
- 提供最小示例，说明中立卡、其他职业卡和特殊类型如何映射音符。
- 只有在接口冻结后再鼓励第三方联动，避免维护负担。

## 五、推荐执行顺序

1. **冻结普通卡池数量**，只做数值、描述和错误修正。
2. **建立自动验证和人工回归表**，优先消灭卡死、残留 UI、牌堆错误和存档问题。
3. **更新 README、审查文档、资源授权和发布包**。
4. **进行多轮平衡测试**，先本地记录，后决定是否启用遥测后端。
5. **增加教程、可访问性和特效精简选项**。
6. **补 2～4 件用于填端口的遗物，并完成声音层收尾**。
7. **发布 1.0 候选版**，只接受错误修复一段时间，不继续扩卡。
8. 1.0 稳定后，再选择挑战/成就、外观、附魔、公共扩展接口等后续方向。

## 六、不建议在首发前做的事

- 再建立一个与音符、演奏、诅咒完全平行的新资源系统。
- 为了显得内容多而继续扩大 80 张奖励池。
- 给每张牌增加大型全屏特效。
- 在未冻结注册键时承诺跨版本存档兼容。
- 在没有隐私说明和关闭入口时启用数据上传。
- 同时开发大量遗物、挑战、皮肤与新剧情，导致核心回归测试无法收敛。
