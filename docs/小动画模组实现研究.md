# 小动画模组实现研究

本记录用于后续开发 MGR 的卡牌动画与战斗特效。研究对象来自工作区外的 `小动画参考` 文件夹；这些参考模组只有编译后的 DLL、少量图片/音频和 Spine JSON，没有源码工程。因此本次通过只读反编译理解其结构，只记录方法与架构，不复制其代码或美术资源。

## 1. 五个参考模组

| 文件夹 | 模组 | 主要对象 | 最值得学习的内容 |
| --- | --- | --- | --- |
| `3770163208` | Perfected Strike: As Depicted | 战士“完美打击” | 单卡完整演出、残影、屏幕闪光、静态立绘替身、Spine 动画注入 |
| `3771349866` | Crash Landing: As Depicted | 储君“坠落” | 落点预告、冲击波、屏幕扭曲、烟尘与碎石、角色位移和地面裁切 |
| `3772619739` | Bullet Time: As Depicted | 猎人“子弹时间” | 跨多张牌持续的视觉状态机、全屏着色器、延迟并集中回放特效与伤害表现 |
| `3773873081` | Voltaic: As Depicted | 机器人“高电压” | 纯代码闪电、角色悬浮、骨骼姿势覆盖、充能球布局和材质联动 |
| `3775606490` | Osty As Depicted | 骨头人的 Osty 相关牌 | 多张牌共用动画绑定层、宠物位移控制器、连招暂驻、战斗结束兜底复位 |

三个 `.spjson` 均为 Spine `4.2.43`：

- `ironclad_psa.spjson`：在战士原动作之外增加 `psa_load`、`psa_sprint`、`psa_slice`、`psa_pose`。
- `regent_cla.spjson`：增加 `cla_launch`、`cla_descent`、`cla_crash`、`cla_recover`。
- `osty_necro.spjson`：增加跳出、戳刺、散架、飞行、重组、点赞等多组动作。

这里的文件不是“只包含新增动作的增量包”，而是可直接替换原骨架数据的完整导出。DLL 会先加载并验证新 skeleton，再把原角色骨架资源的 `skeleton_file_res` 换成它；验证失败便保留原骨架。

## 2. 它们如何接入出牌流程

### 2.1 完全接管单张牌的 `OnPlay`

Perfected Strike、Crash Landing、Voltaic、Bullet Time 以及 Osty 的少数复杂牌，使用 Harmony Prefix 替换原牌的 `OnPlay`：

1. Prefix 把 `__result` 指向自己的异步演出方法并返回 `false`。
2. 演出方法自行重建原牌的命令，例如 `AttackCommand`、施加能力或加入卡牌。
3. 视觉条件不满足时，执行接近原版的普通逻辑作为退路。
4. 动画过程中在正确时刻启动游戏命令，使命中时刻和画面同步。
5. `finally` 无条件恢复人物位置、缩放、颜色、层级、材质和动画。

这种方式控制力最强，也最脆弱。原版牌逻辑、方法签名或战斗流程更新后，复制出来的玩法代码容易过期。MGR 自己的卡可以在卡类内部直接安排演出，无需为了视觉再 Harmony 覆盖自己；对原版牌做纯视觉增强时，除非必须改变命中时刻，不应优先采用完整替换。

### 2.2 在原流程前后挂视觉动作

Osty 大量简单动画使用更轻的办法：

- Prefix 只登记“下一次 Osty 攻击触发应改成哪个动画”。
- Postfix 把附加动画串在原版 `Task` 之后。
- `NCreature.SetAnimationTrigger` 的拦截层消费一次待播放动画，再恢复 `idle_loop`。
- 多张“撞击类”牌共同调用 `SlamTravel.Before/AfterChain`，避免每张牌各写一套移动逻辑。

这更适合 MGR：玩法仍由卡牌和机制类负责，视觉层只接收“开始、命中、结束”事件。以后若为多张演奏牌、星空牌或诅咒牌制作共用演出，应优先建立同类绑定表，而不是复制动画代码。

### 2.3 跨多张牌的持续视觉状态

Bullet Time 并非只播放一次动画，而是建立一个持续到回合结束、敌人死亡或战斗离开的状态：

- 开始时创建全屏滤镜、时钟图片和音频，监听战斗 VFX 容器新增节点。
- 活跃期间逐帧冻结敌人 Spine 时间轴、隐藏或登记部分命中特效、伤害数字、音效和死亡表现。
- 结束时统一让飞行物加速命中，重放缓存特效，刷新血条，播放延迟的死亡动画，然后恢复世界。
- 控制循环每帧检查房间是否还存在、是否仍为出牌阶段、是否还有主要敌人存活；异常时执行硬清理。

这是很有表现力但风险最高的一类实现。它同时修改伤害数字、血条、死亡、屏幕震动、音效、VFX 和战斗结束判定，兼容面很大。MGR 的演奏加速、五线谱发光等只应借鉴“一个状态统一管理生命周期”的思想，不应照搬其对全局战斗表现的广泛拦截。

## 3. 可复用的视觉技术

### 3.1 Godot Tween 负责短时间轴

参考模组普遍用 `CreateTween()` 控制：

- `global_position`：冲刺、跳跃、回位。
- `scale`：落地冲击、呼吸、蓄力脉冲。
- `modulate`：淡入淡出、亮度闪烁、残影消散。
- `rotation`：角色倾斜、覆盖立绘转身。
- 着色器参数：全屏滤镜强度、冲击波距离、颜色混合。

多属性同时变化时使用并行 Tween；明确的先后动作使用串行 Tween 或 `await Cmd.Wait`。时间轴结束后必须销毁临时节点。角色主体 Tween 则必须保存初始值并在 `finally` 恢复。

### 3.2 纯代码绘制比图片资源更灵活

Voltaic 的闪电完全由代码生成：

- 用中点位移递归生成不规则折线。
- 同一条路径叠三层 `Line2D`：宽而淡的外光、中等宽度的辉光、窄而亮的核心。
- 使用加法混合，短时间内重新随机路径形成电弧抖动。
- 分支采用更细、更淡并逐渐收窄的线。
- 设置同时存在的上限，生命周期结束后在 `finally` 递减计数并 `QueueFree()`。

这套方法可直接转化为 MGR 的音符连线、星空电弧、和弦冲击纹或人物周边星座连线。重点不是闪电形状，而是“同路径多层线条 + 加法混合 + 短生命周期 + 数量上限”。

Crash Landing 的落点提示使用运行时创建的径向 `GradientTexture2D`；尘墙复用游戏已有的云朵帧，并用确定性随机数布置大小、角度和延迟。由此可见，简单标记、柔光和冲击圈不必另做图片。

### 3.3 屏幕空间 Shader

Crash Landing 使用读取屏幕纹理的 `canvas_item` shader，在冲击点左右制造向外扩张的折射带。Bullet Time 则用全屏 ColorRect 和 shader 完成：

- 冷色去饱和与暗角；
- 从人物位置向外扩张的多圈扭曲；
- 轻微色差；
- 持续的低幅空间扰动。

兼容性做法值得保留：检测到自定义战斗背景时，Bullet Time 会退化为普通半透明 ColorRect，不强行使用屏幕采样 shader。MGR 若以后加入大招级全屏效果，也应提供无屏幕采样的降级路线。

### 3.4 残影与替身图层

Perfected Strike 有两种做法：

- 残影：复制当前 Spine 身体节点，读取当前动画名和时间，冻结副本时间轴，再淡出销毁。
- 替身立绘：临时隐藏人物 Body，在同一父节点下放置 `Sprite2D`；按期望世界高度自动换算缩放，而不是依赖源图片像素；结束时恢复 Body。

MGR 当前人物是 PNG 序列，不适合直接照搬 Spine track 冻结。对应实现应当复制当前帧使用的纹理或复制当前可见 Sprite/AnimatedSprite 节点，之后停止动画并淡出。替身图层的“按期望显示高度归一化”非常适合未来更换高清素材。

### 3.5 粒子与程序纹理

Perfected Strike 使用 `CpuParticles2D` 制作眼部烟气和滑行尘土，并在代码中生成柔边烟雾纹理。Crash Landing 使用大量短命 Sprite/Tween 制作碎石、土堆和尘墙。两者共同原则：

- 发射器只负责生成，计时结束先停止 Emitting，再延迟销毁，让已发射粒子自然消散。
- 粒子节点挂在战斗 VFX 容器或人物视觉节点，明确局部/全局坐标。
- 高频效果必须限制数量和持续时间。

### 3.6 骨骼姿势的运行时覆盖

Voltaic 不导入一套新动作，而是在 Spine 即将计算世界变换前，按蓄力进度修改若干骨骼旋转；结束时把覆盖量归零并断开回调。它还把影子骨骼逐渐缩小，表现角色离地。

这证明“现有动作 + 少量骨骼程序修正”可以实现新姿势，但依赖具体骨骼名称和 Spine 运行时。MGR 已决定使用 PNG 序列，因此不直接采用；可以用整体旋转、位移、缩放和局部叠加 Sprite 模拟相同意图。

## 4. 生命周期与稳健性：最重要的部分

这些模组真正值得吸收的不是炫技，而是清理策略：

1. 开始前捕获人物的 `GlobalPosition`、`Scale`、`Modulate`、`ZIndex`、材质和动画状态。
2. 每次跨帧后再次检查 `GodotObject.IsInstanceValid`。
3. 战斗房间变化、战斗结束、敌人全部死亡或玩家阶段结束时主动停止控制循环。
4. `try/finally` 恢复人物状态；即使伤害命令或视觉节点报错，也不能把人物留在屏幕外。
5. 玩法命令单独保存为 Task。若动画在启动命令前失败，末尾仍补执行一次；若已启动则只等待，不重复执行。
6. 每个临时节点最终 `QueueFree()`；Tween 被替换前先 `Kill()`；事件监听结束时解除连接。
7. 提供普通表现退路：缺资源、缺动画、测试模式、节点未就绪时仍正常结算卡牌。
8. 长演出要监听主要敌人存活状态。敌人死亡后不再继续无意义的攻击段，只完成必要清理。

这与 MGR 过去出现过的“卡牌悬停中央”“演奏牌结束后数字残留”“敌人死亡后仍继续演奏”属于同一类问题：视觉节点、逻辑任务和归属状态没有在所有出口统一收束。以后新增特效必须先设计退出路径，再设计入场动画。

## 5. 对 MGR 的推荐落地结构

后续新增卡牌特效时，建议维持如下职责，不改动当前已经稳定的演奏牌主体框架：

```text
卡牌/机制逻辑
  └─ 发出纯语义事件：开始、命中、生成音符、触发和弦、演奏结束
       └─ MGR 视觉导演（只决定播放什么）
            ├─ 短时间轴：Tween / await
            ├─ 程序特效：Line2D / Polygon2D / Gradient / 粒子
            ├─ 人物演出：PNG 当前帧替身、位移、缩放、调色
            └─ 生命周期守卫：房间、战斗、敌人、节点有效性、硬清理
```

具体建议：

- 共用效果集中到类似 `MgrCardVfxDirector` 的服务，不让卡牌类持有 Godot 节点。
- 参数继续集中在 `MgrVisualTuning.cs`，不要把颜色、时长和尺寸散落在卡牌代码中。
- 演奏、音符和人物特效分别拥有自己的根节点；页面打开和战斗结束时可整组隐藏或清理。
- 每个异步特效返回 Task，但默认不阻塞玩法命令；只有必须卡准命中时刻的关键动画才等待。
- 普通连续效果设全局并发上限；高频生成时根据本回合次数缩短动画，避免视觉队列反过来拖慢战斗。
- 先调用玩法逻辑还是先播放动画必须逐卡明确，不能把“视觉完成”当作“玩法完成”的唯一信号。

## 6. 可优先用于 MGR 的模式

| MGR 场景 | 推荐借鉴 | 不建议照搬 |
| --- | --- | --- |
| 单张金卡的大招演出 | Perfected Strike 的分段时间轴、残影、闪光和最终复位 | 复制原版卡完整 `OnPlay` |
| 音符生成/和弦触发 | Voltaic 的多层 Line2D、短暂重新随机、并发上限 | 每颗音符创建长期常驻 shader |
| 演奏期间持续加速与发光 | Bullet Time 的单一状态机和逐帧退出检查 | 拦截全局伤害数字、死亡、音效和战斗结算 |
| 星空或万象全屏效果 | Bullet Time 的滤镜渐入渐出与兼容降级 | 永久改写共享材质资源 |
| 群体重击、落地或爆炸 | Crash Landing 的落点提示、冲击折射、尘墙错峰 | 大量无上限 Sprite/粒子 |
| 多张牌共享人物小动作 | Osty 的动画绑定表与共用移动控制器 | 每张牌独立保存、恢复人物状态 |
| PNG 序列人物残影 | 复制当前帧纹理后冻结、淡出 | 调用 Spine track 复制方案 |

## 7. 新特效检查清单

实现任何 MGR 卡牌动画前检查：

- [ ] 特效是否纯视觉；失败后卡牌效果仍会正确结算？
- [ ] 是否明确挂载到正确的战斗 VFX/人物视觉节点，坐标系是否统一？
- [ ] 是否保存并恢复所有被改过的人物属性？
- [ ] 战斗结束、页面切换、敌人死亡、节点销毁时是否会退出？
- [ ] 临时节点、Tween、事件连接和异步任务是否都有清理出口？
- [ ] 多次连续触发时是否有限流、合并或加速？
- [ ] Fast/Instant 模式是否需要缩短或退化？
- [ ] 是否提供缺少资源或动画时的普通表现？
- [ ] 参数是否进入 `MgrVisualTuning.cs`？
- [ ] 是否避免直接修改共享 Resource；必须修改时是否 Duplicate 并在结束后恢复？

## 8. 结论

这五个模组提供了三种成熟路线：Spine 完整动作注入、Godot 程序化短特效、持续视觉状态机。对当前采用 PNG 序列人物的 MGR，最有价值的是后两种，以及 Osty 的“多张牌共享动作控制器”。Spine 注入可以作为理解原版角色动画的参考，但不应重新把 MGR 带回已经放弃的 Spine 接入方案。

今后制作 MGR 特效时，默认顺序应为：先保证玩法任务独立正确，再添加可失败、可跳过、可清理的视觉层；先复用程序绘制和统一状态机，再考虑专用图片资源或全流程接管。
