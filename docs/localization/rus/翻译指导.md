## 0. 独立任务窗口快速启动

本文件不仅是文风说明，也是翻译、审校与交接的操作手册。任何新任务窗口即使看不到既往对话，也必须能够仅凭本文件、目标语言指导、仓库资源和原版参考继续工作；聊天中的临时决定若未写入文档，不视为有效裁决。

开始工作前按顺序完成：

1. 从仓库根目录打开并完整阅读本文件，再完整阅读 `docs/localization/<语言简写>/翻译指导.md`；不得只依赖任务摘要或已有译文。
2. 检查 `MGRMod/localization/zhs/` 是否仍符合本节的源快照；如文件、key 或哈希已变化，先按第 13 节同步基线并更新文档版本。
3. 同时打开本轮文件的简体中文源、原版目标语言同类文件和目标语言术语表；译文必须直接从 `zhs` 产生。
4. 检查工作区现状，保留不属于本任务的已有改动。并行工作时先按第 12 节登记独占范围，严禁两个窗口同时写同一文件。
5. 若目标语言尚未建立，执行第 3 节的“先复制完整 `zhs` 骨架”流程；若已存在，则只补齐结构，不得覆盖已完成译文。
6. 每完成一个独占工作单元，立即执行第 13 节的结构检查和人工复核，并按第 14 节留下交接记录。

### 0.2 语言进度的判定方式

语言是否完成不能由目录存在与否判断。每个语言指导顶部必须写明当前阶段：`仅骨架`、`术语锁定`、`全量翻译中`、`首版完成`、`游戏内审校完成`。只有达到第 10 节全部条件，才能标为“游戏内审校完成”。仓库中 `eng`、`zht`、`jpn`、`kor` 目前已有首版；后续任务仍须以各自指导和实际 QA 结果为准，不得把“首版完成”误当最终定稿。

## 1. 文档效力与翻译依据

翻译任何一个条目时，必须同时使用以下三类依据：

1. **MGR 简体中文文本**：语义、机制、人物性格与创作意图的绝对最高优先级来源。
2. **《杀戮尖塔 2》原版目标语言文本**：游戏既有术语、句法、标点、大小写、数字格式、卡牌描述节奏及人物口吻的最高风格依据。
3. **本总指导及目标语言指导文档**：保证跨文件、跨批次和跨译者的一致性。

发生冲突时按以下顺序裁决：

`MGR 中文语义与机制 > 原版目标语言的既有术语和角色口吻 > 目标语言指导文档 > 译者个人偏好`

这里的“以中文为最高优先级”指中文决定**说了什么、机制如何结算、角色呈现何种性格**；不要求逐字保留中文语序。译文必须像原版目标语言自然写成的游戏文本，而不是中文句式的表面映射。

禁止将英文或任何其他译文作为新语言的中间源。已有 `eng` 目录只能作为待审校旧稿；所有语言均需回到 `zhs` 逐键核对。

## 3. 开始某种语言前的强制准备

不得直接创建或批量填写目标语言 JSON。每种新语言在全量翻译前必须完成：

1. 建立 `docs/localization/<语言简写>/`，例如 `docs/localization/jpn/`。
2. 将本总指导的**完整内容**复制进 `docs/localization/<语言简写>/翻译指导.md`，记录复制时的总指导版本/日期。目标语言指导顶部的版本必须与本文件一致；若不一致，应先同步总指导，再继续翻译。
3. 将 `MGRMod/localization/zhs/` 整个目录复制为 `MGRMod/localization/<语言简写>/` 的初始骨架，包括全部 JSON 文件、key、值、占位符、SmartFormat、富文本标签与非语言数据。若目标目录已存在，先逐文件补齐到与当前 `zhs` 完全一致的结构，再开始翻译；不得用旧目标目录反向覆盖 `zhs`。
4. 对复制后的目标语言目录只逐值翻译可显示自然语言。尚未翻译的值暂时保留中文，使缺漏可见；不得以空字符串、删除 key 或复制旧英文来掩盖未完成项。
5. 在语言指导中追加目标语言特化章节，至少包括：
   - MGR 公共概念的固定译法、词性、大小写/书写形式和禁用译法；
   - 原版游戏常用机制术语对照；
   - 卡牌、遗物、能力、UI、风味文本的句法和标点习惯；
   - MGR 与各先古之民的目标语言口吻说明；
   - 从原版目标语言资源中选取的典型案例；
   - 已确认的专名、双关、文化引用及处理理由；
   - 尚未解决的问题和裁决记录。
6. 完成一组小规模试译案例并审校，通过后才进入全量翻译。

语言特化文档不是一次性前置材料。每次确认新术语、人物口吻或例外时，应先更新该文档，再让后续译文采用新裁决。若总指导更新，各语言指导必须标记“待同步”并补齐更新内容。

## 5. MGR 公共概念登记

本表先固定中文概念的边界与含义，不提前指定各语言译文。目标语言的唯一译法必须登记在该语言指导中；相同概念不得因文件、句式或译者不同而随意换词。

| 中文规范词 | 概念边界/语义 | 使用注意 |
|---|---|---|
| 音符 | MGR 核心资源的统称 | 与一般音乐叙述中的“音符”区分语境，但原则上保持同一核心词根 |
| 音符槽 | 容纳音符并在填满时触发和弦的槽位 | 不得译成牌槽、能量槽或演奏队列 |
| 生成音符 | 创建音符并放入音符槽的机制动作 | 固定使用一种游戏动词；不要在 create/gain/add 等近义词间漂移 |
| 移除音符 | 不结算其效果而移走音符 | 不得与“消耗”或“触发”混用 |
| 结算音符 | 依次应用音符效果 | 与生成、移除严格区分 |
| 触发和弦 | 音符槽填满后发生和弦并结算全部音符 | “触发”与目标语言原版 trigger 类术语保持一致 |
| 和弦 | 音符槽填满时触发的核心机制 | 不得按语境换成和声、组合或旋律 |
| 演奏 | 卡牌进入演奏队列，并在后续回合开始时自动打出的机制 | 既可作关键词，也可作机制动作；两者词根须一致 |
| 演奏次数 | 演奏牌后续自动打出的剩余/指定次数 | “演奏次数增加”只增加队列中该牌的剩余演奏次数，不会当场额外演奏；`EVERYDAY_MIRACLES` 与 `ENCORE` 都适用。译文必须明确“剩余次数”，不得写成“再演奏 N 次”或“立即演奏” |
| 演奏队列 | 放置演奏牌的专用区域 | 与手牌、抽牌堆、弃牌堆、消耗堆并列，是独立区域 |
| 结束演奏 | 一张演奏牌完成或被强制结束其演奏状态 | 不等同于“打出”或“消耗”该牌 |
| 立即进行一次演奏 | 立即触发演奏牌的一次自动打出 | 必须保留“立即”与“一次”的机制信息 |
| 强音 | 强化攻击、技能与能力音符的可叠层能力 | 音乐术语；不要译成普通“力量”或“音量”而丢失专名性质 |
| 起音 | 音符槽为空时触发的卡牌条件 | 不是“战斗开始”或“演奏开始” |
| 尾音 | 音符槽恰好只差一个填满时触发的卡牌条件 | 不是“回合结束”或“演奏结束” |
| 星空 | 生成星空音符而非原卡牌类型对应音符的特殊卡牌身份/机制标记 | 卡牌正文中使用紫色；不是普通“星空”意象时要保留专名一致性 |
| 星空音符 | 触发后获得能量的特殊音符 | 与“星空”身份不同，但建议共享稳定词根 |
| 基础音符 | 攻击、技能、能力、状态、诅咒五类音符的统称 | 不包含星空音符和幽灵音符 |
| 攻击音符 | 对随机敌人造成伤害的基础音符 | 牌类型“攻击”与该音符的词根应对应 |
| 技能音符 | 提供格挡的基础音符 | 牌类型“技能”与该音符的词根应对应 |
| 能力音符 | 抽牌的基础音符 | 采用原版对 Power 牌型的正式译法，不能按日常意义另译 |
| 状态音符 | 给予所有敌人虚弱与易伤的基础音符 | 采用原版 Status 牌型的正式译法 |
| 诅咒音符 | 回复生命的基础音符 | 采用原版 Curse 牌型的正式译法 |
| 幽灵音符 | 给予无实体的特殊音符 | 不属于基础音符 |
| 万象 | 同时具有五种基础音符及星空音符效果的特殊音符/效果 | 必须按定义翻译，不能泛化为“全部音符” |
| 转化为音符 | 消耗目标牌并生成与其牌型对应的音符 | 同时包含“消耗牌”和“生成音符”两层规则；不得弱化为普通转换措辞 |
| 对局中 | 手牌、抽牌堆、弃牌堆、消耗堆及演奏队列的合计范围 | 是有明确定义的范围关键词，不等于泛指“战斗期间” |
| 基础伤害 | 卡牌自身伤害，不含力量、活力等加成 | 使用原版目标语言已有术语 |
| 耗能 | 卡牌费用/能量消耗 | 目标语言采用原版描述费用的标准表达，不自行另造近义词 |

除上述核心术语外，所有原版机制词——如格挡、力量、敏捷、活力、虚弱、易伤、无实体、固有、保留、虚无、消耗、抽牌堆、弃牌堆、消耗堆、手牌、斩杀——必须直接采用原版目标语言中的正式写法。

## 6. 卡牌、能力、遗物与 UI 的风格原则

### 6.1 机制文本

- **先保证信息无损，再追求最短的自然表达。**不得添加、删除或模糊对象、数量、时点、条件、持续时间及结算顺序；在这些机制信息完整的前提下，可以删去重复主语、重复机制名和目标语言中不必要的连接语，也可以重组句子，而不必逐字对应中文。
- 机制专名是否随数量变化，必须由目标语言规则决定。英语紧凑型音符专名 `AttackNote`、`SkillNote`、`PowerNote`、`StatusNote`、`CurseNote`、`StarryNote`、`GhostNote`、`BasicNote` 无论数量多少都保持单数词形；法语、德语、俄语、西班牙语等有正常数与格变化的语言仍须使用合乎语法的词形，不得机械套用英语规则。
- 卡牌和遗物是高频扫读文本，应主动控制字数与玩家的阅读负担。若完整术语已由关键词、悬浮提示或同一句的统领结构明确，可采用原版目标语言中自然的省略、并列或短句；不得为了“完整翻译”重复解释界面已经说明的内容。
- 精简不能制造新的歧义。数量、对象、范围、触发条件、时点、持续时间、结算顺序、牌堆/区域及费用变化均属于不可省略的信息；拿不准时保留较长但明确的版本。
- 每次全量翻译和术语变更后，应按显示长度复查卡牌与遗物描述，优先审校最长文本，并与原版目标语言的简短案例比较。精简后的译文仍须逐项回译核对中文机制。
- 采用原版目标语言的命令式或陈述式习惯，不照搬中文主语与语序。
- 一项完整动作通常占一行；多个独立动作、不同对象或不同结算时点应分行。
- 条件必须紧跟它控制的结果。`起音`、`尾音`、`演奏结束时`等不得互换。
- 卡牌描述的信息层级和显示顺序继续遵守 `docs/localization/CARD_DESCRIPTION_STYLE_GUIDE.md`。目标语言可调整语序，但不能改变信息层级。
- `description` 与 `smartDescription` 是不同运行场景的字段，不能因表面相似就只翻译一个或让两者机制信息不一致。

### 6.2 标题与风味文本

- 卡牌名、遗物名、能力名应保留中文原作的意象、语域、歌曲/文学引用和俏皮感；若直译会失去已知引用，应先登记出处与备选方案再裁决。
- 机制标题与关键词优先保持可识别性；风味文字允许更自然、更有文学性的目标语言表达。
- 卡牌标题默认优先一至两个词或等价的紧凑词组；直译确实无法再压缩时可以使用三个短词，但不得把标题扩写成解释性长句。已有用户裁决的短标题必须优先于更长的官方译名或作品名转写。
- 符号是命名的一部分时要保留其功能，例如 `流☆星☆群`、`ʚ电子♡天使ɞ`、`「 鳥 」`；若目标语言字体或排版不支持，应在语言指导中记录替代方案。
- `「 鳥 」` 的规则分为“文字”和“外框”两层：日语与繁体中文保留汉字 `鳥`；其他语言必须翻译括号内的“鸟”，不能原样残留日文。全角括号 `「 」`、括号内两侧各一个空格属于固定命名结构，任何语言都不得删除、改成半角括号或压掉间距。已锁定示例：英语 `「 Bird 」`、韩语 `「 새 」`、俄语 `「 Птица 」`、法语 `「 Oiseau 」`。新增语言应采用 `「 <目标语言译名> 」`，并将具体结果登记到该语言指导。
- 不得在没有依据时仅凭代码中的英文类名决定译名；但代码名是重要的命名证据。用户明确指出代码名已经提供目标词或要求按代码名翻译时，该裁决高于旧有转写，并须写入修复记录。
- 当前已锁定的短标题裁决见 `docs/localization/卡牌标题简短化修复记录.md`；其中英文标题 `Paranoia Girl`、`Ultramarine Hymn`、`White South Wind`、`Let It Be`、`Resonate`、`Meteor Aftermath`、`Pleasing Ghosts`、`The Light Song`、`Watching You`、`Chaos Magic` 不得被后续作品名检索自动恢复为旧长标题或日语转写。
- `MANIMANI` 的 `Let It Be` 只锁定英语，不是跨语言原样复制的专名。日语必须使用原曲名 `まにまに`，繁中使用 `隨之任之`；其他语言采用各自的简短译名或合适的原题转写，具体映射见修复记录。
- `CHAOS_MAGIC` 使用语言特例：简体与繁体中文保持现有中文标题不改；日语固定为 `混沌メグ`；其他目标语言必须按“混沌魔法”的字面语义翻译，并保证卡牌与同名能力标题完全一致。
- 拟声标题的升级后缀按目标语言的显示长度裁决：简体中文、繁体中文、日语、韩语只追加一个字符（`啊`、`啊`、`あ`、`아`）；目前的拉丁字母语言追加 `aa`，俄语追加 `-а-а`。不得机械地要求所有语言追加两个字符；具体结果见 `docs/localization/卡牌标题简短化修复记录.md`。

#### 6.2.1 歌曲与作品名的检索、确认和定名

每次新增卡牌名或开始一种新语言前，都要进行一次作品名专项检查。2026-08-16 已对当前 `zhs/cards.json` 的 94 个卡牌名逐一执行首轮“`中文名 + Vocaloid`”检索；以后新增卡牌也必须进入同一流程。

1. 先精确检索 `"中文名" Vocaloid`；无有效结果时再依次尝试 `"中文名" ボカロ`、`"中文名" 初音ミク`、可能的日文原题与作者名。
2. **一条官方一手来源即可确认**；没有一手来源时，至少需要两个彼此独立且能同时对上标题、作者与演唱声库/歌手的可靠来源。只在歌词、歌单、翻唱标题或正文中偶然出现同词，不算确认。
3. 常用词、成语或存在多首同名曲的标题必须标为 `待确认`。不能因为搜到任意一首同名曲，就推定它是卡牌的创作来源。
4. 确认后记录中文卡名、key、原曲标题、作者/演唱者、作品类型、各语言固定标题、证据链接和裁决日期。
5. 目标语言定名优先级为：**官方目标语言标题 > 官方国际版/发行平台标题 > 该语言长期通行标题 > 原题转写 > 自行意译**。已有通行歌名时，不重新创造“更顺口”的译名。
6. `zhs` 仍是语义权威源，不因查到原曲而反向改动中文卡名。若中文卡名有装饰符号、改写或主动省略，如 `ʚ电子♡天使ɞ`、`被害妄想携带女子`，其他语言应记录差异并保持卡牌版本的意图，不能静默补字。
7. 标题裁决变化后，必须同步回查所有已完成语言的 `cards.json` 和语言指导；只改指导、不改现有译文不算完成。

## 8. 不可破坏的技术内容

### 8.1 JSON 与键

- 只翻译 JSON 的可显示字符串值；key 必须与 `zhs` 完全一致。
- 保持合法 UTF-8 JSON，正确转义引号、反斜杠和换行；游戏内换行保留为 `\n`。
- `.sfx` 值、资源路径、事件路径、纯数字的 `*-visit` 值等非自然语言数据不得翻译。
- 每种目标语言的文件名和文件集合必须与 `zhs` 对齐。缺键、重复键或多余旧键必须在交付前解决。

### 8.2 占位符与 SmartFormat

以下内容是程序语法，不是自然语言：

- `{Damage:diff()}`、`{Amount}`、`{energyPrefix:energyIcons(1)}` 等变量与格式器；
- `{IfUpgraded:show:...|...}`、`{InCombat:...|}`、`{HasCards:...|}` 等条件分支；
- 分支中的 `|`、冒号、花括号层级及变量名。

翻译可以调整自然语言在占位符周围的位置，但不得改名、删除、重复或破坏占位符。数值、对象、条件与基础/升级分支的对应关系必须保持。

### 8.3 富文本标签与资源标签

- 保留 `[gold]`、`[blue]`、`[red]`、`[color=...]`、`[b]`、`[i]`、`[sine]`、`[jitter]`、`[shake]`、`[rainbow ...]`、`[img]` 等标签的类型、数量、配对与合法嵌套。
- 标签可随被强调的译词整体移动，但不能丢失、无故新增或交叉嵌套。
- `[img]` 内资源路径不得修改。
- 颜色本身含有机制/身份含义时必须保留，不能只保留文字而删除颜色。

## 9. 术语、专名与争议裁决

每个目标语言指导中的术语表至少包含以下字段：

| 中文源词 | 目标语言固定译法 | 词性/变形 | 首次出现 key | 原版依据 | 禁用译法 | 备注/裁决日期 |
|---|---|---|---|---|---|---|

裁决规则：

1. 原版已有同一机制概念：采用原版正式译法。
2. MGR 独有机制：提出不超过 3 个候选，检查音乐含义、游戏可读性、派生词能力和 UI 长度后定稿。
3. 歌曲、文学、科学或网络文化引用：确认来源后再决定保留原文、采用目标语言通行译名、转写或意译。
4. 无法确定时标为 `待裁决`，不得在不同文件中先行使用多个临时译法。
5. 已定术语若必须更改，要记录理由，并全库替换及复查，不能只改新文本。

### 9.1 跨文件镜像字段与同名内容

同一概念经常同时出现在卡牌、能力、关键词、悬浮提示和遗物中。不能只在单文件内保持一致：

- 简体中文完全相同的卡牌名与能力名，目标语言原则上必须完全相同；歌曲、作品名和专名尤其不得在不同文件中分别意译。
- 中文源刻意使用不同装饰时可保留差异，例如卡牌 `ʚ电子♡天使ɞ` 与无装饰能力名；此类例外必须写入目标语言指导。
- 同一能力的 `description` 与 `smartDescription` 必须表达同一机制。动态版只能改变数值、数量分支或程序要求的对象名，不得增加、删除或改变规则。
- 关键词标题、正文着色词和悬浮提示应使用同一个固定词根；语法变形或经明确统领后的短写可以不同，但必须记录在语言指导中。
- 修改任一镜像字段后，必须按中文源值或概念 key 搜索其他文件并同步回查，不能只修正最先发现的一处。

## 10. 质量标准与完成定义

一个语言批次只有同时满足以下条件才能标记完成：

- **语义正确**：机制对象、数量、条件、时点、持续时间、结算顺序与中文一致。
- **原版一致**：基础机制词、同类文本句法和先古之民口吻符合原版目标语言。
- **术语一致**：语言指导内的固定译法在全部资源中一致，变形有记录。
- **技术有效**：JSON 可解析；key 集合对齐；占位符、SmartFormat 与富文本标签通过自动检查。
- **表达自然**：由熟悉目标语言游戏文本的审校视角通读，不呈现明显翻译腔。
- **简洁可扫读**：卡牌和遗物没有不必要的重复说明；较长描述已做专项复查，且精简未损失机制信息。
- **角色可信**：MGR 和每位先古之民仍能仅凭台词被区分。
- **界面可用**：关键卡牌、长能力说明、遗物、选择框和对话在游戏内无严重溢出、断行或缺字。
- **有据可查**：新术语、特殊专名与例外处理均已回写语言指导。

任何自动检查只能证明结构没有明显损坏，不能替代语义、文风和人物审校。

## 11. 禁止事项

- 不得以现有英文译文为其他语言的唯一源文本。
- 不得只做逐字替换或依赖未经审校的机器翻译批量提交。
- 不得修改 key、变量名、资源路径或音效事件。
- 不得为了缩短或让句子顺畅而省略机制条件、数字、对象、时点、持续时间、结算顺序或区域。
- 不得把同一 MGR 机制在卡牌、能力、遗物和提示中译成不同词。
- 不得只参考原版英语来推断日语、韩语等语言的原版风格。
- 不得在没有建立并填写目标语言指导的情况下开始全量翻译。

## 12. 多任务窗口并行协作协议

并行翻译以“减少等待”为目的，不能牺牲单一事实源和可合并性。

### 12.1 可并行与不可并行的边界

- 默认工作单元是“一个目标语言的一个 JSON 文件”；工作量很大时可拆成互不重叠且明确列出 key 前缀的区间。
- 同一时刻一个文件只能有一个写入者。其他窗口可只读审校，但不得同时保存修改。
- `docs/localization/本地化翻译总指导.md`、目标语言指导和术语表是共享裁决源，同一时刻也只能有一个维护者。
- 不同语言或不同文件可以并行；跨文件术语必须先在语言指导中锁定，再开始各工作单元。
- 发现源中文、术语或机制存在疑问时，先登记“待裁决”，暂停受影响的 key；不阻塞无关文件。

### 12.2 领取工作单元时必须记录

```text
语言 / 简写：
总指导版本：
zhs 源快照日期或哈希：
独占文件或 key 范围：
开始状态：仅骨架 / 续译 / 审校
允许修改：目标 JSON；必要时目标语言指导
明确不修改：其他工作单元与无关文件
```

若仓库没有集中任务表，以上内容至少写入该任务窗口的首条工作记录；交接时再写入目标语言指导的变更记录。开始前应查看当前文件差异，若同一文件已有来源不明的未提交改动，应停止写入并先确认归属。

## 13. 源同步与可重复质量检查

### 13.1 中文源更新时的同步流程

1. 重新统计 `zhs` 文件集合、每文件 key 集合与 SHA-256，并更新第 0.1 节和规范版本。
2. 对每个目标语言做 key 差异：新增 key 从 `zhs` 复制中文值作为显眼占位；删除或改名的 key 单独列出，不自动删除目标译文。
3. 对同 key 的中文值变化生成清单，只重译受影响条目；不得重新复制整个目录覆盖既有译文。
4. 检查新增或改动字符串的占位符、标签、歌曲/作品名与术语，再更新各语言指导的同步版本。
5. 完成受影响语言的结构 QA 和人工语义复核后，才恢复“首版完成”或更高状态。

### 13.2 每个工作单元的自动检查

检查脚本可以自行实现，但交付结果至少必须证明：

- 目标 JSON 全部可解析，编码为 UTF-8；文件集合和顶层 key 集合与 `zhs` 完全一致。
- 检查器必须区分“字面 key”与“递归值路径”：`cards.json`、`powers.json` 等文件的顶层 key 本身可能含 `.`，不得按点号拆成对象层级；`ancients.json` 等真实嵌套对象或数组则应递归检查并保留数组索引。若一次修改后突然出现大批同类错误，必须先抽样核对检查器逻辑，再判断资源有误，禁止依据未经验证的批量告警改写译文。
- 没有空值；`.sfx`、资源路径、事件路径与纯数字访问标记等非语言值和中文源完全一致。
- 每个对应字符串的 `{变量:格式器(...)}` 根名与格式器、花括号层级、SmartFormat 分支符 `|` 均未损坏。
- 富文本标签类型、数量、配对和嵌套合法；`[img]` 路径不变。
- 歌曲/作品名符合总指导和目标语言指导的锁定表，`「 鸟 」` 类特殊括号保持全角括号与内侧空格。
- 简体中文同名的卡牌/能力标题在目标语言中一致；`description` / `smartDescription` 的机制对象、条件与时点一致。中文源刻意存在的装饰差异按语言指导中的例外表检查。
- 除明确应保留的专名和字符外，不残留未翻译简体中文；语言自身使用汉字不等于残留，必须结合目标语言规则判断。
- 对卡牌、遗物和能力的最长文本做长度排序并人工检查，确保精简后未丢失机制信息。
- 运行 `git diff --check` 或等效检查，不引入行尾空格、冲突标记或意外格式变化。

### 13.3 自动检查后的人工复核

按“机制对象 → 数字 → 条件 → 时点 → 持续时间 → 结算顺序 → 术语 → 自然度 → 长度”的顺序逐项核对。`cards.json`、`relics.json`、`powers.json` 必须专项检查扫描速度；`ancients.json` 必须按人物连续通读，而不是按孤立句子检查。

## 14. 交接记录与完成报告

任何任务窗口结束前，都要给下一窗口留下可直接执行的记录。最低模板如下：

```text
语言 / 简写：
总指导版本与目标语言指导版本：
zhs 源快照：
已完成文件 / key 范围：
未完成文件 / key 范围：
本轮新增或改变的术语与专名裁决：
仍待裁决的问题及受影响 key：
自动 QA：通过项 / 未通过项：
人工复核：已检查的类型、人物与长文本：
游戏内验证：已验证 / 未验证，具体范围：
工作区注意事项：现有差异及不得覆盖的文件：
建议下一步：
```

状态定义：

- `仅骨架`：已复制 `zhs`，尚无可靠译文。
- `术语锁定`：核心术语、原版机制词和语言风格已确定，允许试译。
- `全量翻译中`：已有通过试译的规则，仍存在中文占位或未审校文件。
- `首版完成`：全部 key 已翻译且结构 QA 通过，尚未完成充分游戏内排版与母语级终审。
- `游戏内审校完成`：满足第 10 节全部完成定义，可作为发布候选。

若没有游戏内验证证据，报告中必须明确写“未验证”，不可用“完成”暗示已经验证界面效果。
