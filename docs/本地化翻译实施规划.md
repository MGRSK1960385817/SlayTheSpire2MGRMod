# MGR 模组本地化翻译实施规划

> 本规划只定义翻译工作的准备、顺序、审校与验收。本阶段不开始正式翻译。  
> 中文权威源：`SlayTheSpire2MGRMod/localization/zhs/`  
> 总规范：`docs/本地化翻译总指导.md`  
> 分语言模板：`docs/语言特化翻译指导模板.md`

## 1. 当前基线

### 1.1 MGR 中文资源

截至 2026-08-16，`zhs` 目录包含 9 个 JSON 文件、516 个键：

| 文件 | 键数 | 内容 |
|---|---:|---|
| `ancients.json` | 148 | MGR 与先古之民对话及音效/访问数据 |
| `card_keywords.json` | 32 | MGR 核心机制与音符解释 |
| `cards.json` | 203 | 卡名、描述、选择提示和动态文本 |
| `characters.json` | 16 | 角色信息、短台词、代词和解锁文本 |
| `potions.json` | 6 | 药水名称与效果 |
| `powers.json` | 70 | 能力名称、静态说明和动态说明 |
| `relics.json` | 33 | 遗物名称、效果和风味文本 |
| `settings_ui.json` | 2 | 设置界面文字 |
| `static_hover_tips.json` | 6 | 对局中、基础伤害、转化为音符等提示 |

键数只用于建立本次基线。正式翻译开始前必须重新生成清单，因为中文仍可能继续开发。

### 1.2 现有英文目录的处理

仓库已有 `localization/eng/`，9 个文件与中文大体对齐，但它是**既有译稿而非权威源**。当前盘点还发现 `characters.json` 比中文少 1 个 key。第一梯队英语工作应按“逐键对照中文与原版英语、审校或重译”的方式进行，不能直接宣布现有目录完成。

### 1.3 原版语言事实

原版当前支持 15 个游戏简写：

`eng, zhs, zht, deu, esp, fra, ita, jpn, kor, pol, ptb, rus, spa, tha, tur`

其中 `spa` 是西班牙（欧洲）西语，`esp` 是拉丁美洲西语。完整映射见总指导。

## 2. 优先级与建议推进顺序

同一梯队内原则上逐语言完成“指导—试译—全量—QA”，避免同时开启过多未收口语言。

| 梯队 | 语言 | 建议顺序 | 说明 |
|---|---|---|---|
| 第一 | `jpn` 日语、`eng` 英语 | `jpn` 与 `eng` 可先后独立推进 | 最高优先；英语已有旧稿，重点是系统审校 |
| 第二 | `zht` 繁体中文、`kor` 韩语 | `zht` → `kor` | 繁中不可只做字形机械转换，仍需术语和区域表达审校 |
| 第三 | `deu` 德语、`fra` 法语、`rus` 俄语 | `deu` → `fra` → `rus` | 注意复合词、性数格、文本长度等不同风险 |
| 第四 | `spa` 西班牙西语、`esp` 拉美西语、`ptb` 巴葡 | 先确定目标西语变体，再做另一变体与 `ptb` | 两套西语必须分目录、分指导、分审校 |
| 第五 | `ita` 意大利语、`pol` 波兰语、`tha` 泰语、`tur` 土耳其语及未来新增语言 | 按需求与译者资源排序 | 新增语言还需先确认游戏加载支持、字体和代码映射 |

如果一次只计划发布一种西班牙语，应由项目负责人先明确选择 `spa` 或 `esp`；规划阶段暂不替用户做区域市场决定。

## 3. 每种语言的标准流水线

### 阶段 0：冻结中文翻译基线

1. 确认本轮翻译对应的中文提交或快照。
2. 统计每个 JSON 的 key 数，记录中文文件哈希或提交号。
3. 将翻译期间新增/改动的中文 key 记入变更队列，避免静默漂移。
4. 检查中文源自身是否存在占位符、标签或机制描述问题；有疑问先修中文再翻译。

产物：本轮基线记录、中文资源清单、待澄清问题列表。

### 阶段 1：建立语言特化指导

1. 新建 `docs/<lang>/翻译指导.md`。
2. 完整复制最新总指导，再追加并填写语言模板章节。
3. 对照原版目标语言的同类资源，确定原版机制术语与句法。
4. 定稿 MGR 核心术语，记录禁用译法与语法变化。
5. 为 MGR 及 9 位先古之民建立口吻规则和原版案例。

门槛：核心术语和人物口吻尚未定稿时，不进入全量翻译。

### 阶段 2：代表性试译

建议选择约 20–30 个显示字符串，覆盖：

- 简单、复杂、起音、尾音、演奏、星空与 SmartFormat 卡牌；
- 关键词/悬浮提示；
- `description` 与 `smartDescription`；
- 遗物效果与风味文字；
- 选择提示、设置说明；
- MGR 与每位先古之民至少一组完整来回。

试译需同时通过机制准确性、原版风格、术语一致性、技术结构和游戏内排版检查。所有新裁决回写语言指导。

### 阶段 3：按依赖顺序全量翻译

建议文件顺序：

1. `card_keywords.json`、`static_hover_tips.json`：先固定核心概念。
2. `powers.json`：验证机制术语和动态说明。
3. `cards.json`：最大机制文本主体。
4. `relics.json`、`potions.json`：沿用已稳定术语并处理风味文字。
5. `characters.json`、`settings_ui.json`：角色与界面文本。
6. `ancients.json`：最后集中做人物口吻与对话连贯性审校。

翻译以小批次推进，建议每批 25–50 个可显示字符串。每批完成后立即做结构检查和术语复查，不把错误积压到全部文件完成后。

### 阶段 4：双层审校

每批至少经过两种不同视角：

1. **机制/源文审校**：逐键对照中文，确认数量、对象、条件、时点和结算顺序。
2. **目标语言/文风审校**：不依赖中文语序通读，确认自然度、原版术语、角色口吻与界面长度。

若资源允许，最终由目标语言母语或高度熟练审校者复核。机器翻译、回译或自动术语检查可以辅助发现问题，但不能作为最终审校者。

### 阶段 5：自动 QA

至少检查：

- 所有 JSON 均可解析；
- 目标语言与 `zhs` 的目录、文件和 key 集合一致；
- 无意外空字符串、残留简体中文或明显占位文本；
- 占位符名称、次数与格式器一致；
- SmartFormat 花括号、分支与嵌套合法；
- BBCode/富文本标签类型、数量、闭合与嵌套一致；
- `.sfx`、资源路径及 `*-visit` 数据未被翻译；
- 数值及机制关键词没有在翻译过程中丢失；
- 固定术语没有出现未经登记的变体。

自动 QA 应输出可重复运行的报告；发现问题后修复并重新运行，而不是人工勾掉错误。

### 阶段 6：游戏内 QA

至少覆盖：

- 角色选择与角色介绍；
- 卡牌普通查看、升级预览、战斗内动态数字；
- 卡牌关键词与右侧悬浮提示；
- 能力的静态和动态说明；
- 遗物、药水、选择界面和设置界面；
- 每位先古之民对话的标签、换行、音效字段与按钮；
- 长文本、窄 UI、特殊符号、目标语言字体和缺字情况。

对日语、韩语、繁中、俄语、泰语等文字系统，字体覆盖与断行必须作为独立验收项。

### 阶段 7：发布与后续同步

1. 记录完成时使用的中文基线。
2. 生成目标语言完成报告和已知问题。
3. 发布前再与当前中文做一次 key 与内容差异扫描。
4. 中文后续变更时，以 key 为单位标记目标语言为 `新增`、`源文已改/待重译` 或 `已同步`。
5. 术语变更必须全语言回查，不仅修改触发变更的单个条目。

## 4. 工作单元与状态管理

建议按“语言 × 文件 × 批次”管理，不以整个语言只有“未做/完成”两个状态。

推荐状态：

`未开始 → 术语准备 → 试译 → 初译 → 机制审校 → 语言审校 → 技术 QA → 游戏内 QA → 完成`

每个批次至少记录：

- 语言简写、文件名、key 范围或明确 key 清单；
- 中文基线提交/日期；
- 翻译者和审校者；
- 新增术语/裁决；
- 自动检查结果；
- 游戏内检查范围；
- 未解决问题。

不得用“文件已存在”或“所有值非空”代替“翻译已完成”。

## 5. 建议的自动化检查设计

正式翻译启动时，建议新增一个只读校验脚本，输入 `zhs` 与目标语言目录，输出 JSON 或 Markdown 报告。脚本至少包含以下规则：

| 检查 | 严重级别 | 说明 |
|---|---|---|
| JSON 无法解析 | 阻断 | 文件不可用 |
| 缺文件/缺 key/多余 key | 阻断 | 会导致回退、旧文本或维护漂移 |
| 占位符或格式器不一致 | 阻断 | 可能报错或显示错误数值 |
| 标签不配对/集合异常 | 阻断 | 可能破坏显示 |
| `.sfx`、路径、visit 数据变化 | 阻断 | 非翻译字段被误改 |
| 空值或占位文本 | 阻断 | 未完成翻译 |
| 残留中文 | 警告 | 专名可能合法，需白名单 |
| 术语表外变体 | 警告 | 需语言审校判断词形变化 |
| 文本长度显著膨胀 | 警告 | 提醒进行 UI 检查，不自动判错 |

脚本不能简单要求译文标签字符串与中文逐字符同序；目标语言可能需要移动带标签的词组。正确检查目标是标签类型、数量、配对、嵌套与语义附着均有效。

## 6. 风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 中文持续改动 | 译文刚完成就失效 | 冻结基线、记录哈希/提交、维护源文变更队列 |
| 多语言术语漂移 | 同一机制多种译法 | 语言指导先行；新裁决先入表再入文本 |
| 借英语转译 | 语义损失被层层放大 | 每种语言逐键回看 `zhs`，英语仅作目标语言时处理 |
| 原版风格误判 | 译文像通用软件而不像游戏 | 按资源类型和同一人物检索原版目标语言案例 |
| 角色声音趋同 | 先古之民无法区分 | 建角色口吻矩阵，集中通读每位角色全部台词 |
| SmartFormat 损坏 | 运行时报错或显示模板 | 自动解析/比对，复杂条目单独测试 |
| UI 溢出或缺字 | 文本被截断、字符方框 | 语言级长度策略、字体检查、游戏内截图复核 |
| 西语变体混淆 | `spa` 与 `esp` 互相覆盖 | 分目录、分指导、分术语表和分审校 |
| 繁中机械转换 | 地区术语不自然或游戏术语不一致 | 以原版 `zht` 为风格依据，字形转换仅作初始辅助 |
| 既有英文被高估 | 有文件但存在漏键/旧译 | 逐键重新审校，按同一完成定义验收 |

## 7. 各梯队启动条件

开始一个新梯队前，应满足：

- 上一梯队每种计划发布的语言已完成，或未完成项有明确冻结理由；
- 总指导中发现的共性问题已回写；
- 自动 QA 能覆盖上一梯队暴露的结构问题；
- 中文基线已重新确认；
- 新语言有足够的目标语言审校能力。

可以在等待某语言母语审校期间准备下一语言的原版语料与指导文档，但不应因此把未经审校的上一语言标为完成。

## 8. 本规划阶段的交付边界

本阶段只交付：

- 原版语言与简写核对结果；
- 总翻译原则、核心概念、人物口吻与技术约束；
- 分语言指导模板；
- 分梯队的实施、审校、QA 与维护方案。

本阶段明确不做：

- 不创建新的目标语言本地化目录；
- 不批量填写或修改任何目标语言 JSON；
- 不把现有英文目录宣告为已完成；
- 不提前裁决各目标语言的 MGR 专属术语。
