## 三、当前数据能够分析什么

### 直接服务 MGR 平衡的数据

建议保留：

- 对局结果：胜负、进阶、到达节点、时长、重载次数。
- 版本：游戏版本、模组版本、遥测结构版本。
- 最终卡组：卡牌 ID、升级层数、附魔、加入层数。
- 卡牌奖励：每次出现的候选、玩家选择或跳过的结果。
- 卡牌变化：获得、移除、升级、降级。
- 最终遗物与遗物选择；药水获得、使用和丢弃。
- 商店购买、休息点选择、事件与先古选项。
- 每节点生命、金币、受伤、回复、获得与花费金币。
- MGR 机制总计：音符种类、和弦次数、和弦效果结算次数、演奏触发次数、伤害来源。
- `tracking_complete`、`reload_safe`：版本 7 起用于确认存档内的聚合计数可用；重载次数不再自动令数据失效。

这些数据可以回答：

- 哪些卡出现很多但很少被选择；哪些卡选择率异常高。
- 某张卡被选后，胜率、到达层数、战损和卡组构成如何变化。
- 音符、演奏与直接攻击在不同卡组中的贡献比例。
- 卡组攻击端、防御端、过牌端与费用端是否失衡。
- 某些遗物、药水、事件选项是否与异常胜率相关。

### 可选诊断数据

下列字段不是纯卡牌分析的核心，但能解释“为何某张牌在某类战斗中表现异常”：

- 遭遇 ID、死亡遭遇 ID。
- 每场战斗回合数。
- 节点类型与路线。
- 每节点战损。

建议至少保留“遭遇 ID + 回合数 + 战损”，但移除逐个怪物 ID。一个遭遇 ID 通常已经能够唯一描述怪物组合；逐怪物列表既重复又增加体积。

## 四、明确冗余或不适合平衡分析的数据

### 1. PostHog 自动附加的精确网络与地理信息

CSV 包含：

- 原始 IP；
- 城市、经纬度、邮编、时区、省份和国家；
- `$set` 与 `$set_once` 中再次重复的整套地理数据。

这些精确字段不服务 MGR 平衡分析，且增加隐私负担。最终决定是在本地分析数据中只保留一份国家和城市，丢弃原始 IP、经纬度、邮编、时区及人物属性副本。

### 2. PostHog 导出模板中的空列

`elements_chain`、`$group_0..4`、issue 相关字段等在两条记录中全部为空。这些是 PostHog 通用导出列，并非 MGR 主动上传的数据。无需修改模组，只需让下载脚本选择需要的列，不再保存这些空列。

### 3. 运行环境细节

`dotnet_runtime`、操作系统完整版本、进程架构、RitsuLib 编译配置和构建渠道对卡牌平衡无用。建议：

- 保留游戏版本、MGR 版本和 RitsuLib 版本，方便排查版本差异；
- 不进入日常平衡分析表的字段：完整 OS 版本、`.NET` 版本、架构、RitsuLib build configuration/channel。

这些字段可以留在原始事件外壳用于技术排障，但下载成平衡分析表时应剔除。

### 4. 逐房间怪物列表

当前每个房间同时记录遭遇 ID 和怪物 ID 列表，例如：

`SLIMES_WEAK` + `LEAF_SLIME_S/TWIG_SLIME_M/TWIG_SLIME_S`

对常规固定遭遇而言，怪物列表是遭遇 ID 的重复展开。建议删除 `rooms[].monsters`，保留：

- `rooms[].id`：遭遇 ID；
- `rooms[].turns`：战斗回合数；
- 必要时保留 `rooms[].type`。

如果将来存在同一遭遇 ID 动态生成不同怪物组合，再恢复怪物列表也不迟。

### 5. 选择结果与获得记录的重叠

样本中被选中的卡同时存在于：

- `card_choices[].card` 且 `picked=true`；
- `cards_gained[]`。

两者在普通卡牌奖励中重复，但 `cards_gained` 还可能包含事件、商店或特殊效果获得的牌，所以不能简单整体删除。建议长期方案是统一成一组“卡牌变动记录”，额外标记来源；短期维持现状更安全。

`ancient_choices`、`event_choices`、`relic_choices` 也存在部分语义重叠，但各自仍能表达候选项、实际事件文本键和获得结果，不建议在只有两局样本时贸然删掉。

## 五、“第一层初始卡组”是否应删除

当前并没有每层重复上传完整卡组；完整卡组只在 `final_player.deck` 中上传一次。里面的 `floor_added=1` 初始牌看似冗余，但有三个用途：

1. 判断玩家最后保留了哪些初始牌、删掉了哪些；
2. 判断初始牌是否升级或附魔；
3. 正确还原最终卡组大小和卡牌比例。

因此不建议从原始上传中删除初始牌。更合适的方式是：

- 原始数据继续保留完整最终卡组；
- 分析表中把“未升级、未附魔、仍保持默认数量的初始牌”折叠成摘要；
- 单独计算“初始打击删除数、初始防御删除数、初始牌升级数”等指标。

如果直接删除初始牌，将无法区分“玩家主动删除了打击”和“遥测根本没有记录打击”。

## 六、当前发现的数据质量问题

### 1. `base_note_slots` 两局均为 0（已决定移除）

MGR 初始应有音符槽，因此 `0` 明显不可信。当前代码读取的是原版 `BaseOrbSlotCount`，它更接近机器人充能球底层字段，不一定保存 MGR 自定义音符槽数量。

已经决定不采集音符槽容量：字段与对应的数值过滤均从遥测结构中移除。

### 2. 首层 `hp_healed` 实际是初始生命赋值

两局的先古节点分别记录回复 67 和 53 点生命，显然不是玩家在先古节点真实治疗，而是历史系统把初始生命状态计入了回复量。

版本 7 已将第一个先古节点的该值归零。

### 3. 致死战斗的 `damage_taken` 为 0

两局死亡节点都记录 `current_hp=0`，但该节点 `damage_taken=0`。这说明原版地图历史可能在战斗正常结束时才完整写入战损，玩家死亡时没有填充。

版本 7 会在保留原版逐次记录的同时，用“上一节点生命 + 本节点回复 - 当前生命”反推生命损失，取两者较大值，以补齐致死或直接改变生命的路径。

### 4. 总伤害与来源伤害不守恒

第二局记录的是**人物对敌人造成的实际生命伤害**，不是人物受到的伤害：

- 原版总伤害：135；
- 卡牌伤害：70；
- 音符伤害：54；
- 其他伤害：0；
- 差额：11。

根因已经确认：原版 `DamageDealt` 在每次穿透格挡的伤害后直接增加；MGR 分类计数此前挂在 `AfterDamageReceived`，而原版在该次伤害杀死目标时不会调用这个回调。因此所有斩杀伤害会进入原版总伤害，却不会进入 MGR 来源分类；本局差额 11 点很可能就是斩杀伤害合计。

分类计数现已移动到每次伤害都会调用、包含斩杀伤害的 `AfterDamageGiven`，并与原版一样只统计由 MGR 玩家作为伤害来源的 `UnblockedDamage`。版本 7 还新增 `unclassified`，在出现新的未覆盖伤害路径时自动补足与原版总伤害的差额；如果已分类伤害反而超过原版总数，整条记录会被硬校验拒绝。旧样本无法追补缺失的 11 点。

### 5. 极短路线但超长时长

第一局只到第二节点，却持续 1221 秒。这不是非法数据，但说明总时长包含暂停、停留或其他非操作时间。建议后续同时记录战斗回合数或有效战斗时间；至少不要单独用 `duration_seconds` 衡量卡组效率。

## 七、推荐的删减优先级

### 建议立即从分析下载结果中移除

- 原始 IP、经纬度、邮编、时区及 `$set/$set_once` 地理副本；国家和城市各保留一份；
- PostHog issue、group、elements 等空列；
- `.NET`、完整 OS、进程架构、RitsuLib 编译配置；
- `rooms[].monsters`；
- 旧 `request_id=run_history` 和开发期旧模组 ID 的测试数据。

这些删减不影响当前模组上传逻辑，可以先在下载/整理脚本中完成。

### 建议修正后再使用

- 首层 `hp_healed`；
- 致死节点 `damage_taken`；
- `damage_by_source` 与 `damage_dealt` 的口径。

### 暂时不要删

- 完整最终卡组，包括初始牌；
- 卡牌奖励候选及选择；
- `cards_gained/removed/upgraded/downgraded`；
- 遗物、药水、事件、先古、商店与休息点记录；
- 遭遇 ID、回合数、节点类型；
- MGR 音符、和弦、演奏及伤害来源合计。

## 八、当前样本能得出的决策边界

目前只有两局，而且一局几乎没有发生有效战斗，不能据此调整任何卡牌数值、掉率或流派强度。现阶段数据最适合做以下工作：

1. 验证上传、授权、去重和版本过滤；
2. 校验字段是否真实、守恒、无重复；
3. 确定下载脚本的精简列；
4. 为以后累计到数十或数百局后的卡牌选择率、胜率与机制贡献分析打基础。

从版本 7 起，先用 `Test-MgrTelemetryData.ps1` 对下载记录做守恒性检查，再用至少 30 局 `tracking_complete=true` 且 `reload_safe=true` 的记录做第一轮趋势观察；若要评价单张卡，通常还需要更多样本并控制进阶、获得层数和卡组环境。
